# Agent استدلالی محلی با Ollama — تمرین ۱ درس LLM Agents

این برنامه مسائل استدلالی چندمرحله‌ای (فارسی، با فرمت پاسخ مشخص‌شده در متن مسئله) را با مدل **محلی**
`qwen3.8:27b` روی Ollama حل می‌کند. ایده‌ی اصلی: به‌جای یک بار پرسیدن از مدل، **دو روش مستقل** مسئله را حل
می‌کنند و فقط وقتی پاسخ پذیرفته می‌شود که با هم توافق داشته باشند؛ در غیر این صورت یک داور و در نهایت رأی‌گیری
تصمیم می‌گیرد.

- **بدون هیچ وابستگی شخص ثالث**: فقط کتابخانه‌ی استاندارد پایتون (≥ ۳.۹) و REST API خود Ollama.
- **کاملاً آفلاین**: تنها اتصال شبکه، درخواست به Ollama محلی است (`127.0.0.1:11434`)؛ تنظیمات proxy سیستم نادیده
  گرفته می‌شود تا درخواستی به جای دیگری نرود.
- **خروجی همیشه JSON معتبر**: فایل خروجی قبل از شروع با پاسخ خالی ساخته و بعد از هر مسئله به‌صورت اتمیک بازنویسی
  می‌شود؛ حتی با Timeout، قطع Ollama یا خطای داخلی.

## نصب

```bash
# ۱) Ollama (نسخه‌ی 0.32.12 یا جدیدتر — مدل qwen3.8 به این نسخه نیاز دارد)
ollama --version
# ۲) دریافت مدل ارزیابی
ollama pull qwen3.8:27b
# ۳) پایتون ≥ 3.9 — هیچ پکیجی لازم نیست (requirements.txt عمداً خالی است)
pip install -r requirements.txt
```

## اجرا (رابط استاندارد)

```bash
python main.py --input input.json --output output.json
```

ورودی می‌تواند یک شیء `{"id": ..., "problem": ...}` یا لیستی از آن‌ها باشد (و `{"problems": [...]}`)؛ خروجی هم‌شکل
ورودی است: `{"id": ..., "answer": "..."}`. فیلد `answer` فقط شامل پاسخ نهایی با فرمت خواسته‌شده است.

نمونه: `python main.py --input examples/sample_input.json --output out.json`

### تنظیمات اختیاری

| آرگومان | متغیر محیطی | پیش‌فرض | توضیح |
|---|---|---|---|
| `--model` | `AGENT_MODEL` | `qwen3.8:27b` | نام مدل در Ollama |
| `--host` | `OLLAMA_HOST` | `http://127.0.0.1:11434` | آدرس سرور Ollama |
| `--time-budget` | `AGENT_TIME_BUDGET` | `300` | سقف زمان هر مسئله (ثانیه) |
| `--max-calls` | `AGENT_MAX_CALLS` | `6` | سقف تعداد فراخوانی LLM برای هر مسئله |
| `--log-dir` | `AGENT_LOG_DIR` | `logs/` کنار `main.py` | محل لاگ اجرا (`none` = غیرفعال) |
| `--no-warmup` | `AGENT_WARMUP=0` | — | بارگذاری مدل قبل از مسئله‌ی اول را رد کن |
| — | `AGENT_NUM_CTX` | `16384` | طول context ارسالی به Ollama |
| — | `AGENT_THINK_REASONER` / `_PROGRAMMER` / `_VERIFIER` / `_TIEBREAK` | `medium` / `low` / `medium` / `medium` | سطح thinking هر نقش |
| — | `AGENT_MAX_CALL_SHARE` | `0.4` | سهم حداکثری یک فراخوانی از بودجه‌ی زمان مسئله (جلوگیری از مصرف کل بودجه توسط یک فراخوانی طولانی) |
| — | `AGENT_CODE_TIMEOUT` | `20` | سقف زمان اجرای برنامه‌ی تولیدشده (ثانیه) |

مقدار نامعتبر در یک متغیر محیطی (مثلاً `AGENT_MAX_CALLS=six`) اجرا را متوقف نمی‌کند: با یک هشدار نادیده گرفته
می‌شود و مقدار پیش‌فرض به کار می‌رود.

## معماری

```
input.json ─► خواندن مسائل ─► ساخت output.json با پاسخ‌های خالی
                    │
                    ▼  برای هر مسئله (بودجه‌ی زمان + سقف فراخوانی)
     FormatSpec ◄── استخراج فرمت پاسخ از متن مسئله (قطعی، بدون LLM)
                    │
      ┌─────────────┴──────────────┐
      ▼                            ▼
  Reasoner (think=medium)     Programmer (think=low)
  حل گام‌به‌گام زبانی          نوشتن برنامه‌ی پایتون که همه‌ی حالت‌ها را
  → «FINAL ANSWER: x»         جست‌وجو می‌کند → اجرا در sandbox → مجموعه‌ی S
                              (در صورت خطا: یک بار اصلاح با پیام خطا)
      └─────────────┬──────────────┘
                    ▼
          توافق: x ∈ S ؟ ── بله ─► پاسخ      (حالت معمول: فقط ۲ فراخوانی)
                    │ خیر / یکی شکست خورد
                    ▼
          Verifier (داور): مسئله + پاسخ‌ها + کد برنامه را می‌بیند؛ قیود را شماره می‌زند و برای
          هر پاسخ، راه‌حل کاملش را می‌سازد و هر قید را PASS/FAIL می‌کند (خروجی برنامه
          ادعایی برای بررسی است، نه اثبات) ─ با یکی از قبلی‌ها یکی شد؟ ─► پاسخ
                    │ خیر
                    ▼
          Tie-break (نمونه‌ی مستقل با seed دیگر) ─► رأی اکثریت
          (برنامه‌ای که چند پاسخ معتبر یافته به هر پاسخِ مجموعه‌اش نیم رأی می‌دهد؛
           در تساوی: داور > برنامه > tie-break > reasoner)
                    ▼
          نرمال‌سازی به فرمت دقیق (در صورت نیاز یک فراخوانی Formatter)
          اگر باز نامعتبر بود و نامزد معتبری وجود داشت ─► همان نامزد معتبر (format-fallback)
```

### چرا این طراحی؟

- **دو روش واقعاً مستقل**: در زنجیره‌ی کلاسیک Planner → Solver → Verifier، همان مدل کار خودش را بررسی می‌کند و
  معمولاً اشتباه خودش را تأیید می‌کند. توافق «استدلال آزاد» و «فرمال‌سازی + محاسبه» شاهد بسیار قوی‌تری است.
- **مکمل بودن خطاها**: خطای غالب مدل در این مسائل حساب‌وکتاب است (فراموش‌کردن یک قید، اشتباه محاسباتی) که برنامه
  مرتکب نمی‌شود؛ نقطه‌ی ضعف برنامه ترجمه‌ی غلط مسئله است که مسیر استدلالی آن را می‌گیرد.
- **کم‌هزینه**: در حالت معمول فقط ۲ فراخوانی؛ مراحل اضافه فقط هنگام اختلاف و فقط اگر بودجه‌ی زمان اجازه دهد.

### لایه‌ی فرمت پاسخ (`agent/answer_format.py`)

فرمت خواسته‌شده از متن مسئله استخراج می‌شود: الگو (`Name=<integer>, ...`)، فهرست گزینه‌ها، «فقط عدد صحیح»،
«فقط عدد» (اعشار مجاز)، «کد n رقمی»، «فقط حرف» یا آزاد. هر پاسخ مدل (با Markdown، پیشوند «FINAL ANSWER:»، ارقام
فارسی و...) به رشته‌ی **دقیقاً** مطلوب تبدیل می‌شود و اگر ممکن نباشد نامعتبر علامت می‌خورد. اگر مدل بعد از پاسخ
توضیح داده باشد (`x = 480 (since ...)`، `480 because ...`، `۴۸۰ زیرا ...`) و کل متن معتبر نباشد، توضیح بریده
می‌شود؛ پاسخی که خودش معتبر است هرگز تغییر نمی‌کند. مقایسه‌ی پاسخ‌ها با کلید کانونیک انجام می‌شود
(`480` و `480.0` و `۴۸۰` یکی‌اند). اعداد به‌صورت متن و دقیق پردازش می‌شوند، نه با `float`؛ بنابراین عدد صحیح
بزرگ (مثلاً `9007199254740993` یا ۲۵!) و اعشار طولانی (`3.14159265`) هیچ رقمی از دست نمی‌دهند و گرد نمی‌شوند.

**بررسی نهایی قبل از نوشتن خروجی:** اگر پاسخ برنده با فرمت خواسته‌شده نخواند، اول همان پاسخ به Formatter داده
می‌شود (که اجازه‌ی تغییر اعداد را ندارد). اگر باز نامعتبر بود و نامزد معتبر دیگری وجود داشت، پرپشتیبان‌ترینِ آن‌ها
نوشته می‌شود (مسیر `format-fallback` در لاگ). فقط وقتی هیچ نامزد معتبری نیست بهترین پاسخ موجود نوشته می‌شود،
چون طبق صورت تمرین پاسخ با فرمت نامعتبر و پاسخ خالی هر دو غلط حساب می‌شوند و پاسخ خالی قطعاً غلط است، ولی پاسخ
موجود ممکن است درست باشد (اگر فرمت از متن مسئله اشتباه تشخیص داده شده باشد).

### سیاست ابهام

بعضی مسائل (حتی در مجموعه‌ی Public) بیش از یک پاسخ معتبر دارند. برنامه همه‌ی پاسخ‌های سازگار با قیود را گزارش
می‌کند؛ اگر پاسخ مسیر استدلالی یکی از آن‌ها باشد پذیرفته می‌شود (خوانش طبیعی از میان پاسخ‌های صوری معتبر انتخاب
می‌کند) و در لاگ `ambiguous=true` ثبت می‌شود؛ وگرنه داور با دیدن کل مجموعه تصمیم می‌گیرد.

### امنیت اجرای کد (`agent/sandbox.py`)

کد تولیدشده توسط مدل: (۱) با AST بررسی می‌شود — فقط ماژول‌های مجاز کتابخانه‌ی استاندارد (`math`, `itertools`,
`fractions`, ...) و بدون `open/exec/eval/__import__/input`، بدون `getattr/setattr/delattr`، بدون دسترسی به
ویژگی‌هایی که با `_` شروع می‌شوند (جز چند مورد بی‌خطر مثل `__init__` و `__name__`) و بدون ویژگی‌هایی مثل `.os`
که از ماژول‌های مجاز به سیستم‌عامل می‌رسند؛ (۲) در یک پوشه‌ی موقت، در پردازه‌ی جدا با `python -I` اجرا می‌شود؛
(۳) با Timeout و در لینوکس با محدودیت CPU، حافظه و حجم خروجی. این یک لایه‌ی محافظ برای کدِ مدل است، نه مرز
امنیتی در برابر مهاجم.

## رعایت قوانین تمرین

- تمام inference از طریق Ollama محلی است؛ هیچ API ابری استفاده نمی‌شود.
- هیچ پاسخ یا متنی از ۱۰ سؤال نمونه در کد، پرامپت‌ها، تست‌ها یا مثال‌ها نیست؛ پرامپت‌ها عمومی‌اند. تست‌ها فقط از
  مسائل و مقادیر ساختگی استفاده می‌کنند. ابزار ارزیابی روی سؤال‌های نمونه، بیرون از این پوشه نگه‌داری شده و برنامه آن را
  نمی‌خواند.
- محدودیت زمان و تعداد فراخوانی هر مسئله قابل تنظیم است و رعایت می‌شود (پیش‌فرض ۳۰۰ ثانیه و ۶ فراخوانی)؛ زمان اجرای
  برنامه‌ها هم از همین بودجه کم می‌شود و هیچ فراخوانی بیش از ۴۰٪ بودجه را نمی‌گیرد.
- بارگذاری مدل (warm-up) یک بار قبل از مسئله‌ی اول و بیرون از بودجه‌ی مسائل انجام می‌شود: این بارگذاری در هر
  حال لازم است و اگر داخل بودجه‌ی مسئله‌ی اول بیفتد، فراخوانی اول آن مسئله را به Timeout می‌کشاند. زمان آن در خط
  خلاصه‌ی لاگ ثبت می‌شود (`warmup_seconds`، و `total_seconds` برای کل اجرا). اندازه‌گیری روی پاد ارزیابی: بارگذاری
  سرد از دیسک شبکه‌ای حدود ۱۵۰ ثانیه، و تقریباً صفر وقتی مدل از قبل در حافظه است؛ روی دیسک محلی معمولاً کمتر است.
  سقف انتظار برای آن ۶۰۰ ثانیه است و شکست آن اجرا را متوقف نمی‌کند. اگر برای کل اجرا سقف زمانی وجود دارد، بهتر
  است مدل پیش از اجرا بارگذاری شده باشد (مثلاً `ollama run qwen3.8:27b ""`).

## نتایج ارزیابی (مدل qwen3.8:27b، Ollama 0.40.13، یک GPU با ۲۴ گیگابایت)

ارزیابی به‌صورت جعبه‌سیاه و دقیقاً با رابط استاندارد انجام شد، روی ۱۰ سؤال Public و ۶۰ مسئله‌ی تازه که با
تولیدکننده‌ای جدا از این پوشه ساخته شدند (همان ۱۰ نوع مهارت با نام‌ها و اعداد جدید، به‌علاوه‌ی نسخه‌های
سخت‌تر؛ یکتایی پاسخ هر مسئله با جست‌وجوی کامل تأیید شده است). خط مبنا همان مدل با **یک** فراخوانی است.

| مجموعه | Agent | خط مبنا (یک فراخوانی، thinking روشن) | خط مبنا (یک فراخوانی، thinking خاموش) |
|---|---|---|---|
| Public (۱۰) | **۱۰/۱۰** | ۹/۱۰ | ۱۰/۱۰ |
| تازه (۲۴) | **۲۴/۲۴** | ۲۴/۲۴ | ۲۳/۲۴ |
| تازه، دیده‌نشده (۲۴) | **۲۴/۲۴** | ۲۴/۲۴ | ۲۴/۲۴ |
| سخت (۱۲) | **۱۲/۱۲** | ۱۱/۱۲ | ۱۲/۱۲ |
| **جمع (۷۰)** | **۱۰۰٪** — میانگین ۲٫۰۷ فراخوانی، ۳۸ ثانیه | ۹۷٫۱٪ — ۱ فراخوانی، ۱۸ ثانیه | ۹۸٫۶٪ — ۱ فراخوانی، ۱۹ ثانیه |

- خطاهای خط مبنا دقیقاً همان خطاهایی است که این طراحی برایش ساخته شده: دو بار «استدلال بی‌پایان» تا Timeout
  (پاسخ خالی) و یک بار کپی‌کردن متن قالب به‌جای پاسخ. در هر سه مورد Agent با مسیر برنامه یا داور درست پاسخ داد.
- مسیر تصمیم Agent در ۷۰ مسئله: ۶۶ توافق مستقیم (۲ فراخوانی)، ۱ توافق در مسئله‌ی چندجوابی، ۳ داوری (هر سه درست).
- در یک اجرای میانی با پرامپت قبلی داور، نتیجه ۶۹/۷۰ بود: برنامه یک قید را اشتباه کدنویسی کرده بود و داور که کد را
  «برنامه‌ای که همه‌ی حالت‌ها را شمرده» می‌دید به آن اعتماد کرد. پرامپت داور به بررسی قیدبه‌قید (PASS/FAIL) تغییر کرد و
  نتیجه‌ی بالا با همین نسخه‌ی نهایی است.
- هزینه: حدود دو برابر خط مبنا در تعداد فراخوانی و زمان؛ سقف هر مسئله ۶ فراخوانی و ۳۰۰ ثانیه.
- پس از این اجرا دو اصلاح قطعی دیگر اعمال شد (پردازش دقیق اعداد و بررسی نهایی فرمت؛ پرامپت‌ها تغییر نکردند).
  بازپخش همه‌ی ۷۲۲ پاسخ نامزدِ ثبت‌شده در چهار دور ارزیابی با کد جدید هیچ پاسخ معتبری را تغییر نداد.

## لاگ‌ها

هر اجرا یک فایل `logs/run-<زمان>-<pid>.jsonl` می‌سازد: برای هر مسئله نوع فرمت، مسیر تصمیم (`consensus`,
`consensus-ambiguous`, `verified`, `vote`, `fallback`, `format-fallback`, `empty`)، همه‌ی پاسخ‌های نامزد، و برای هر فراخوانی LLM:
نقش، سطح thinking، تعداد توکن، زمان و خطا؛ کد برنامه‌هایی که مدل نوشته هم در لاگ می‌ماند تا قابل بازبینی باشد.
خط آخر فایل خلاصه‌ی اجراست (تعداد فراخوانی‌ها، زمان حل، زمان بارگذاری مدل و زمان کل). لاگ‌ها روی stderr هم چاپ
می‌شوند.

## تست‌ها

```bash
python -m unittest discover -s tests -v
```

۹۴ تست با کتابخانه‌ی استاندارد: لایه‌ی فرمت، sandbox، کلاینت Ollama، سیاست orchestrator (با مدل جعلی)، و تست
سرتاسری `main.py` در برابر یک سرور جعلی Ollama (بدون نیاز به مدل).
